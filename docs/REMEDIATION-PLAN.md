# mado — Remediation Plan

> Generated 2026-05-31 by a 9-agent design workflow (7 parallel work-stream architects + destination-first master sequencer + adversarial plan reviewer). Companion analysis: [GAP-ANALYSIS.md](./GAP-ANALYSIS.md). Sequenced per CSE Operating Principle #0 — destination first, then the path; Cell/Grid is restructured exactly once.

## Destination

The destination is a single mado where (1) ONE render-mode-agnostic input/UX engine drives both the embedded-tear default path and the local-PTY fallback over identical inputs, so every capability is implemented exactly once and 'proven once holds in every mode' is structurally true; (2) the terminal is capability-honest — a single typed TerminalCaps value is the source of truth that TERM, DA replies, DECRQM, XTGETTCAP, and terminfo all PROJECT from, and a capability cannot be advertised unless its implementing path exists; (3) all visual, config, and notification work routes through substrate-owned typed primitives (engawa RenderGraph, shikumi ConfigCoverage, tsuuchi dispatch) rather than mado-local one-offs. The whole program is shaped by two hard constraints: Cell/Grid must be restructured exactly ONCE (so wide-attrs + logical-line reflow + paged/CoW groundwork + 256-palette + threading-damage-protocol are co-designed into one wave), and the unified input engine is the prerequisite seam for mouse/copy/paste/search/IME-in-default plus the entire power-user tier. The eight-milestone path leads with the destination per CSE Operating Principle #0: M0 ships the S-effort correctness/honesty wins (delete the Rhai stub, the TerminalCaps primitive, the fleet dead-knob invariant, paste-safety) in parallel from day one because they gate nothing; M1 builds the unified InputEngine seam; M2 performs the single Cell/Grid touch; M3 routes visuals through engawa consuming the new grid; M4 wires the dead config/notification/cwd paths through the unified drain; M5 fills the protocol gaps under the honesty gate; M6 layers the power-user keyboard tier on the unified router; M7 lands the single automation surface plus the deferred architecture/fonts/a11y behind named milestones. Each milestone consumes the prior with no rework because the touch-once constraints are honored by sequencing.

## Sequencing rationale

Destination-first, then prerequisites, then quick-correctness-wins-in-parallel. The ordering logic has three intertwined chains. CHAIN 1 (the seam): A (M1) is the prerequisite for mouse/copy/paste/search/IME-in-default and ALL of F — so it lands second, right after the no-dependency quick wins. CHAIN 2 (touch-once): B's Cell/Grid restructure (M2) must precede C's styled-underline RENDER (M3) and reflow, and must be co-designed with D's SGR-wire-acquisition + 256-palette and G's threading-damage-protocol, so the grid is restructured ONCE in M2 — every later stream consumes the new shape rather than re-forking. C2 underline geometry (M3) is explicitly gated on the M2 grid model being final. CHAIN 3 (honesty gate): D's TerminalCaps primitive (M0) lands FIRST even though it initially advertises a NARROWER set than the current over-claimed xterm-ghostty, because the honesty test must exist to gate every later capability flip — caps for styled-underline start pinned false and unpin in M3 when geometry exists; protocol caps flip in M5 when the esc_dispatch/origin-mode/XTGETTCAP arms land. The quick wins (M0: delete Rhai, ConfigCoverage invariant, dead-knob sweep, paste-safety, TERM honesty) are surfaced as the earliest milestone precisely because they have no shared-surface dependency and can ship in parallel with M1 from day one — blocking them behind the XL refactors would be the path-of-least-resistance inverted. New `Attrs` struct carrying: a small bitset for the boolean attrs (bold/italic/inverse/dim/hidden/strikethrough/overline + a REAL blink the renderer reads), plus a typed `UnderlineStyle` enum {None, Single, Double, Curly, Dotted, Dashed} and a typed `UnderlineColor` enum {Default, Indexed(u8), Rgb(Color)}. Attrs lives inside Style (interned), so widening it does not widen Cell. UnderlineStyle/UnderlineColor are the geometry/paint inputs that engawa's underline node consumes — mado owns the per-cell *which-style* decision; engawa owns the *how-to-draw-that-style* geometry.

C. LOGICAL-LINE GRID. Grid stops being a flat VecDeque<Vec<Cell>> of physical rows and becomes a VecDeque of `Line { cells: Vec<Cell>, wrapped: bool }` where `wrapped == true` means "this physical row continues onto the next without an intervening hard newline" (set by put_char's autowrap, cleared by hard newline/CR-LF/explicit cursor moves). A *logical line* is a maximal run of physical Lines joined by wrapped-flags. resize(cols) becomes REWRAP: concatenate each logical line's cells, re-flow them at the new column count, re-split into physical Lines with fresh wrapped-flags. This fixes reflow_on_resize (currently a dead knob; Grid::resize truncates at terminal.rs:488-515) at the data-model level.

D. MARKS ANCHOR TO LOGICAL LINES, NOT PHYSICAL ROWS. prompt_marks/user_marks currently store absolute grid-row indices (terminal.rs:1650, :1703) shifted by the `evicted` count from scroll_region_up (:434). Reflow changes physical row count, which would silently corrupt these. Destination: a stable monotonic `LogicalLineId` (u64, never reused, assigned at line creation) stamped on each logical line; marks reference (LogicalLineId, intra-line offset). Reflow and eviction preserve marks for free because the id is invariant under rewrap. This is the piece that makes reflow actually safe rather than just visually plausible.

E. PAGED/CoW GROUNDWORK. Lines carry a `seqno`-style dirty stamp already; the destination additionally makes the scrollback half of the VecDeque a Vec<Arc<Line>> so cold scrollback lines are shared/immutable (CoW: a write to a scrollback line — which only happens via reflow — clones). Hot visible lines stay owned Vec<Cell>. This is the memory-layout restructure the brief wants done in the same pass; v1 can land the Line/LogicalLineId/Arc-boundary types and keep eager allocation, with the paging itself deferred — but the TYPES are shaped for it now so Cell/Grid is never touched again for Phase 4.

**Approach.** Co-design all three (wide attrs + logical-line reflow + paged groundwork) around ONE insight: the StyleTable interning that already exists (terminal.rs:264-348) is the shared hinge. Widening attrs is cheap because attrs live in the interned Style; style-dedup for paging IS interning; the Cell-shrink is already flagged as ready. So the single refactor is: (1) move fg/bg/attrs off Cell into Style-only, (2) fatten Attrs inside Style with UnderlineStyle/UnderlineColor/overline/real-blink, (3) wrap rows in a Line{cells,wrapped,logical_id} type, (4) re-anchor marks to LogicalLineId, (5) shape the scrollback as Arc<Line> for future CoW.

KEY PATTERNS:
- Interning as the universal lever: one StyleTable change serves attrs-widening + per-cell-shrink + paging style-dedup.
- Typed enums over bit-packing for underline (UnderlineStyle/UnderlineColor) — the saturated-u8 lesson is exactly what BoundedFontSize taught: a saturated primitive is a bug waiting to surface. Make the new states representable as types.
- Logical-line model = the standard wrapped-flag-per-row reflow algorithm (Alacritty/Ghostty pattern): rewrap = unwrap-to-logical + reflow-to-new-cols + resplit. Keep the EXTERNAL boundary (visible_rows()/viewport_rows() yielding row slices, snapshot_grid yielding GridSnapshot) byte-identical so search.rs/selection.rs (which consume &[Vec<Cell>] by viewport (row,col)) and the 648 scenario tests need zero changes to their coordinate model.

### F — Power-user Ergonomics (modal keyboard tier: vi/copy mode, hints, command palette, regex/incremental search, leader chords, runtime theme/font + OS dark-mode follow)  *(effort: XL)*

**Depends on:** A — unified input/UX path (the shared input_router + single Action dispatch + Terminal handle both embedded and local drive; WS-F inserts the mode machine as the router's first stage and CANNOT land before A), E — live config-reload APPLY (the watcher→apply callback WS-F's set_theme/set_font_family/set_min_contrast setters are called from; the dead-knob invariant test WS-F's min_contrast/follow_system fields must satisfy)

**Destination.** A modern power-user keyboard tier for mado where every advanced interaction is a state transition in ONE awase-driven keyboard-mode state machine, and every visible surface (search bar, command palette, quick-select hints) is an egaku widget rendered through mado's existing overlay pipeline. The end state:

- There is exactly ONE `KeyboardModeMachine` (mado-local) layered on top of the WS-A unified input module. It holds an `awase::BindingMap` with named modes — `insert` (passthrough=true: keystrokes flow to PTY via WS-A's `madori_key_to_pty_bytes`), `normal` (passthrough=false: keyboard scrollback navigation + motions), `visual` (passthrough=false: selection extends under motions), `search` (incremental query capture into an `egaku::TextInput`), `hints` (label capture), `palette` (filter capture into `egaku::TextInput` + `egaku::ListView`). The default mode is `insert`, so a fresh terminal behaves like a normal terminal until the operator presses the leader/enter-normal-mode chord. Mode is the single source of truth for "where does this keystroke go" — the bifurcation between embedded and local paths is impossible by construction because both call the same machine.

- The vi/copy mode is keyboard-driven scrollback navigation + selection that REUSES the existing `selection::Selection` and `search::SearchState` state machines unchanged — the new code is only the motion vocabulary (h/j/k/l, w/b/e, 0/$, gg/G, Ctrl-u/Ctrl-d, /?n N) mapping to `Selection::start/update/finish/select_word` and scrollback offset deltas. No new selection model.

- Hints/quick-select is an `egaku`-overlay label assignment over URL spans + (eventually) any regex-matched span, letting the operator act on text (open URL, copy span, paste span) with two keystrokes and no mouse. It REUSES mado's existing URL detection (`url.rs`) for the first span source and the existing selection→clipboard path for the action.

- The command palette is an `egaku::Modal` + `egaku::TextInput` (filter) + `egaku::ListView` (fuzzy-filtered command list) whose command universe IS the `keybind::Action` enum plus a small set of palette-only verbs — every operator-reachable action is discoverable + invokable by name. The palette dispatches into the SAME `Action` handler WS-A owns, so there is one action-dispatch chokepoint.

- Search is upgraded to incremental (re-query on every keystroke — already true in main.rs) + regex (opt-in via a mode toggle) by widening `search::SearchState` to hold a compiled matcher enum (Literal | Regex) behind one `matches_line` method; the `regex` crate is the only new dep, gated so headless tests still run.

- Leader/chord sequences are `awase::KeyChord` entries in the BindingMap — the substrate already implements leader→follower with timeout + the `ChordState` machine; WS-F only authors mado's chord table. The leader chord itself (enter-normal-mode / open-palette) is a new fleet intent on the ishou atlas so it converges across mado/namimado/escriba.

- Runtime theme/font switching + OS light/dark follow + min-contrast are wired through WS-E's config-apply callback: the apply path resolves `ishou_tokens::FleetTheme`/`ResolvedTheme` (or a named `theme::Theme`) into the renderer's live color table + cell metrics WITHOUT a restart, and a macOS appearance observer (built on the existing `platform::is_dark_mode`) flips the resolved theme when `theme.follow_system` is set. min_contrast becomes a live renderer knob that adjusts foreground luminance against background per WCAG, killing one of the dead config knobs.

The discipline: mado owns ONLY the mode state machine + the motion/action vocabulary + the renderer-side overlay draw + the runtime-apply glue. Everything reusable (the mode/chord/condition machine, the overlay widgets, the theme tokens, the bounded refinement of contrast) lives in the owning substrate crate (awase / egaku / ishou-tokens). New cross-app concepts (vi-leader, palette-open, copy-mode-yank intents) land on the ishou FleetKeybinds atlas, not in mado-local config, so namimado/escriba inherit them.

**Approach.** BUILT ON WS-A. WS-F assumes WS-A has already produced a single shared input module (call it `input_router`) that both `gui_tear_attach.rs` and `main.rs` drive, exposing: (a) a `Terminal`/pane handle for grid reads + scrollback offset + send-bytes; (b) a single `Action` dispatch function; (c) the `KeybindManager` lookup. WS-F inserts the keyboard-mode machine as the FIRST stage of that router and adds three overlay widgets the router consults before falling through to PTY.

ARCHITECTURE (layers, top = first to see a keystroke):

1. `KeyboardModeMachine` (mado-local, new module `keyboard_mode.rs`). Wraps one `awase::BindingMap`. Each mado mode = one `awase::KeyMode` with `passthrough` set correctly (insert=true, all others=false). Per-keystroke flow:
   - Convert the madori KeyEvent → `awase::Hotkey` via the EXISTING `keybind::madori_modifiers_to_awase` + `madori_key_to_awase` helpers (no new conversion code).
   - Call `BindingMap::match_key(hotkey, ctx)`. The result drives everything:
     - `Matched { action, consume }` → run a `ModeAction` (mode-local verb: motion, mode-switch, overlay-open, or a passthrough to the shared `keybind::Action` dispatch). `consume` decides whether the PTY ever sees it.
     - `ChordPending` → the leader is held; render an optional which-key hint overlay; consume.
     - `Remapped`/`NoMatch` → in `insert` mode (passthrough), fall through to WS-A's `madori_key_to_pty_bytes`; in any non-passthrough mode, drop (modal capture).
   - `MatchContext` carries `mode: "normal"|"visual"|...` so the SAME chord can mean different things per mode using awase's existing `Condition` machinery (no mado-local branching ladder).

2. `ModeAction` enum (mado-local) — the vocabulary the machine dispatches. Three families:
   - **Motions/edits** (normal/visual): `CursorLeft/Down/Up/Right`, `WordForward/Back/End`, `LineStart/LineEnd`, `Top/Bottom`, `HalfPageUp/Down`, `StartVisual`, `Yank`, `ExitToInsert`. Each manipulates a mado-local `CopyModeCursor { row, col }` + the existing `Selection` (StartVisual=`sel.start`, motion=`sel.update`, Yank=`sel.extract_text`→clipboard→`ExitToInsert`).
   - **Mode/overlay switches**: `EnterNormal`, `OpenPalette`, `OpenHints`, `OpenSearch{regex}`, `ClosePalette/Hints/Search`.
   - **Delegate**: `Action(keybind::Action)` — palette + chords reuse the existing copy/paste/scroll/fullscreen handlers verbatim.

3. Overlay widgets (egaku, substrate). Each is a thin mado-local *adapter* over an egaku state machine + a renderer draw call:
   - **Search bar**: `egaku::TextInput` for the query (replaces the hand-rolled `query.push_str/pop` loop in main.rs:819-853) + the existing `search::SearchState` for matches. The router routes keystrokes to the TextInput while `mode==search`; on each edit it calls `SearchState::set_query`.
   - **Command palette**: `egaku::Modal` (visible flag) + `egaku::TextInput` (filter) + `egaku::ListView` (filtered `Action` names). `mado::CommandPalette` holds the catalog `Vec<(&'static str label, ModeAction)>`, fuzzy-filters via a small matcher, and on Enter dispatches `selected → ModeAction`.
   - **Hints**: `mado::HintsOverlay` holds `Vec<HintSpan { label: String, range, action }>` assigned from `url.rs` URL spans (first source). egaku isn't strictly needed here (it's a label-capture state machine), but `egaku::TextInput`-style incremental label matching is reused for multi-char labels.

4. Renderer overlay draw (mado-local, in `render.rs`). One new `OverlayState` the renderer reads each frame: which overlay is active + its egaku state. Reuses the EXISTING selection-overlay quad pipeline + glyph atlas to draw the search bar / palette list / hint labels — no new GPU pipeline (engawa owns underline/sixel/shader geometry per the ownership map; the palette/hint boxes are plain quads + text mado already draws). DESTINATION NOTE: the palette/hint chrome (rounded box, label badge) is a candidate for an engawa "overlay-chrome" node family once a second consumer (ayatsuri command palette) appears — flagged, not built now (three-site rule).

5. Runtime theme/font + dark-mode follow (mado-local glue over ishou + WS-E):
   - WS-E's config-reload callback (currently logs only) gains a real apply: diff old vs new `MadoConfig`; for theme/font/contrast deltas, call new renderer setters `set_theme(&ResolvedTheme)`, `set_font_family(&str)` (re-resolve cosmic-text face + recompute cell metrics + push new cols/rows to tear), `set_min_contrast(f32)`.
   - `theme.follow_system: bool` (new typed field) wires a macOS `NSDistributedNotificationCenter` observer for `AppleInterfaceThemeChangedNotification` in `platform.rs` (objc2, pure-safe, sibling of existing `is_dark_mode`). On flip, re-resolve `FleetTheme`→light/dark variant and apply via the same `set_theme` path. min_contrast uses `ishou_tokens::Refined<f32, ContrastBounds>` (substrate) so the value is bounded by type (0.0..=1.0) — same primitive class as BoundedFontSize.
